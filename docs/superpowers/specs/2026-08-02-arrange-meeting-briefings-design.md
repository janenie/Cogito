# 会议席位与资料分发任务设计

## 目标

在现有 `COGITO_3_Lobby.tscn` 中增加白名单玩法
`arrange_meeting_briefings`，利用 CEO 办公室、档案室、休息室和会议室现有空间，测试玩家的
关系推理、约束满足、空间理解、跨区域调查和任务内记忆。玩法不复制 Lobby，不依赖实验室或
移动平台，也不新增美术资产。

玩家需要在三个固定区域读取各一份会议记录，把三条关系线索合并为唯一座次，再将李明、
王芳、陈宇、赵宁四位参会者的可搬运资料放到会议桌对应席位，最后使用一次性的 Verify 按钮提交。

## 范围

本次实现包括确定性谜题生成、任务专用场景和 Monitor、可搬运资料、可信吸附放置、公开
briefing、200 次 `act` 请求硬上限、跨层终局白名单、文档和自动化测试。

可信侧推理效率指标不进入现有桥协议、MCP 结果或公开轨迹；本次只预留集中事件入口，不扩展
公开 DTO。真实外部模型的多局验收不属于自动化实现范围，必须在用户另行确认截图、令牌费用和
本地轨迹持久化后进行。

## 非目标

- 不把线索、答案、候选解、回合种子或内部席位 ID 放进 briefing、观察结果或日志。
- 不要求依赖物理投掷、刚体落点或提交瞬间的世界坐标判定答案。
- 不改变普通 Lobby、已有任务、既有可读纸张或已有书本的行为。
- 不在本轮增加新模型、材质、纹理、音频或动画资源。
- 不强制玩家按固定顺序调查或使用某一种推理过程；成功只取决于最终可信世界状态。

## 方案选择

采用“独立任务子场景 + 纯回合模型 + 专用 Monitor + 专用席位交互”的组合：

- 子场景负责所有可调位置的可见对象：任务记录、资料、资料名、席位标记、顺时针标记、Verify、
  出生点和任务卡锚点。
- 纯回合模型只负责 24 种排列、线索生成和线索求解，不访问场景树，便于穷举测试。
- Monitor 负责本局隐藏答案、世界启停、资料—席位可信映射、提交和终局。
- 专用席位交互负责从玩家手中接收任务资料、释放、对齐、吸附和占用拒绝。

现有 `CogitoSnapSlot` 以单一 `PackedScene` 和物体名称为主要匹配条件，并通过通用区域事件处理
放入和取出，不能直接表达四份有身份的资料、每席一份以及 Monitor 的逻辑占用。因此本任务不
修改通用 SnapSlot，而增加范围受限的任务专用席位组件。

## 场景结构与任务隔离

新增小型子场景 `AIPlayArrangeMeetingBriefingsSetup`，作为 Lobby 根节点的一个实例。它包含：

- 入口 `PlayerSpawn` 和 `TaskCardAnchor`；
- CEO 办公室、档案室和休息室各一份任务专用可读记录；
- 会议室电视附近现有侧桌上的四份资料及资料名标签；
- 会议桌周围四个可见席位标记和交互区域；
- 桌面的 `↻ CLOCKWISE` `Label3D`；
- 会议室出口附近一个现有 `GenericButton` 实例作为 Verify。

四份资料复用 `carryable_books.tscn`，三份记录复用现有可读纸张外观。它们是任务专用实例，
不得重命名或复用其他任务的逻辑对象。资料名 `Label3D` 作为资料刚体的子节点随资料移动，并以
适合近距离读取的双面或 Billboard 显示方式配置。

`AIPlayController` 增加直属子节点 `ArrangeMeetingBriefingsMonitor`，其导出
`scenario_id = "arrange_meeting_briefings"`。Monitor 必须先调用父 Controller 的
`is_requested_scenario()`。未选中本任务时：

- Setup 根节点保持隐藏、不处理且不参与物理；
- 所有任务专用碰撞、交互、资料和记录禁用；
- 不生成回合、不连接任务信号、不移动玩家、不改写任务卡；
- Verify 和席位不出现在可交互探测中；
- 普通 Lobby 和现有任务的纸张、书本、家具和路径保持不变。

选中任务后，Monitor 才启用 Setup，初始化回合，写入三份世界记录，移动玩家和任务卡，并连接
资料、席位及 Verify 的任务信号。任务卡使用任务专属纸张，不复用 Demo Hint 模型；任务期间
扫描、隐藏并禁用原 Lobby 的全部 `Read hint` 对象。退出场景树时断开由 Monitor 添加的连接；
测试重复实例化不得留下共享状态。

## 席位与空间语义

四个公开环境席位使用以下可信内部 ID：

- `tv_side`：电视侧；
- `door_side`：会议室门侧；
- `opposite_tv`：电视对面侧；
- `inner_wall`：内墙侧。

从会议桌正上方观察，顺时针环固定为：

```text
tv_side → door_side → opposite_tv → inner_wall → tv_side
```

因此 `tv_side` 与 `opposite_tv` 相对，`door_side` 与 `inner_wall` 相对；环上前后相邻的席位
互为相邻。桌面 `↻ CLOCKWISE` 标签和四个席位的环境名称必须在玩家站立视角下可读，且位置与
上述环一致。世界内的地点、席位、任务卡、顺时针和 Verify 标签只显示英文；四位参会者仍使用
两字中文姓名。线索文本使用中英双语席位名称以及“顺时针下一席”等公开名称，不公开内部 ID。

四份资料使用固定内部 ID：

- `atlas`
- `birch`
- `crown`
- `delta`

内部 ID 不向玩家显示；世界中的可见名称始终为两字中文名：`李明`、`王芳`、`陈宇`、`赵宁`。

## 可信回合模型

非零 `round_seed` 直接作为 `RandomNumberGenerator.seed`；零值使用运行时随机种子。对于给定
有效 seed，生成过程必须完全确定，且不依赖 Dictionary 遍历顺序、场景帧率或物理事件顺序。

每局按固定顺序生成：

1. 洗牌四个席位，形成 `folder_id → seat_id` 的一对一隐藏答案；
2. 从隐藏答案推导所有为真的候选线索；
3. 规范化并去重候选线索；
4. 枚举所有三线索组合，保留满足唯一性和最小性的组合；
5. 用同一 RNG 从合格组合中确定性选择一组，并确定性打乱三条线索顺序；
6. 洗牌 CEO 办公室、档案室和休息室，把三条线索一对一分配给三份记录。

模型枚举四份资料到四个席位的全部 24 种排列。每条候选线索必须与隐藏答案一致，并采用以下
规范类型：

- `exact_seat(folder, seat)`：某资料属于某环境席位；
- `adjacent(folder_a, folder_b)`：两份资料相邻；
- `opposite(folder_a, folder_b)`：两份资料相对；
- `clockwise_next(from_folder, to_folder)`：后者位于前者的顺时针下一席；
- `not_seat(folder, seat)`：某资料不属于某环境席位。

对称关系把两个资料 ID 按固定次序规范化；方向关系保留方向；完全相同的语义线索只能出现
一次。每条单独线索还必须排除至少一个排列，避免无效陈述。

一组三线索只有同时满足以下条件才可选：

- 三条线索共同过滤后只剩隐藏答案；
- 删除任意一条线索后至少剩两个排列；
- 三条线索没有语义重复；
- 每条线索都与隐藏答案一致且确实缩小其输入候选集。

因为只处理 24 个排列和有限真线索集合，生成器应穷举合格组合，而不是依赖有次数上限的随机
重试。若程序错误导致某答案没有合格组合，模型必须显式失败并阻止任务开始，不得降级为非唯一
或非最小谜题。

模型可以提供测试用快照，包含 seed、隐藏答案、规范线索和记录分配；该接口只能被 Godot 单元
测试调用，不能被 Controller、Bridge、Observer、MCP、轨迹记录器或面向玩家的错误信息调用。

## 线索记录与公开信息

三份记录的位置固定，但每局线索分配随机：

- CEO 办公室；
- 档案室；
- 休息室。

记录标题清楚说明区域和“会议记录”，正文仅含一条自然语言线索及必要的资料/席位公开名称。
不显示线索类型名、内部 ID、候选数、序号暗示、答案或 seed。玩家可以重复阅读；读取本身不会
提供正确性反馈，也不改变谜题。

入口任务卡标题为“会议席位与资料分发”，内容公开：

- 必须分别调查 CEO 办公室、档案室和休息室的会议记录；
- 李明、王芳、陈宇、赵宁四位参会者的资料要分别放到会议桌四个环境席位；
- 席位由电视、会议室门、电视对面和内墙区分；
- `↻ CLOCKWISE` 定义“顺时针下一席”的方向；
- 已放资料可以在提交前拿起重放；
- Verify 只能按一次，缺失或放错都会立即失败。

任务卡不包含本局三条线索原文、隐藏排列、线索分配、候选解、seed 或内部节点信息。任务卡弹框
必须在单屏内完整显示正文并禁用垂直滚动；三份记录仍使用大尺寸读取弹框。

## 资料放置与取回

每个席位包含可见标记、独立交互区域和唯一吸附 Transform。专用席位组件只接受四个由 Monitor
登记的任务资料；手持普通 Lobby 物体与席位交互时拒绝操作且不改变世界。

玩家手持有效资料与空席位交互时，按以下顺序执行：

1. 确认本局未冻结、席位为空、手中对象属于本任务；
2. 请求现有 `CarryableComponent` 正常 `leave()`，避免绕过玩家持物状态；
3. 清零刚体线速度和角速度，将其冻结并对齐到席位吸附 Transform；
4. 记录该席位的 `folder_id`，并通知 Monitor 原子更新可信映射；
5. 保持资料的拿取交互启用，使其在提交前可以重新调整。

已占用席位拒绝第二份资料，不释放玩家手中对象、不替换原资料，也不改变可信映射。交互提示可以
说明席位已占用，但不能说明现有资料是否正确。

当已吸附资料再次进入被携带状态时，席位组件和 Monitor 必须立即清除该席位占用及对应的
`folder_id → seat_id` 关系，然后允许现有 Carryable 流程解除冻结。逻辑清除不能等待资料离开
碰撞区，也不能依赖下一物理帧。重复的拿起/离开信号必须幂等。

Monitor 在任何时刻维护双向一致的可信状态：每份资料最多一个席位、每个席位最多一份资料。
提交判定只读取该逻辑映射，不根据刚体当前位置、重叠区域或视觉距离猜测答案。

## Verify 与终局

Verify 复用现有 `GenericButton`，设置为不可重复使用。Monitor 收到第一次有效 `pressed` 时：

1. 先设置 `_round_finished` 并冻结本局交互；
2. 禁用四份资料、四个席位和 Verify 的后续任务交互；
3. 复制当前可信 `folder_id → seat_id` 映射；
4. 检查是否恰好包含四份唯一资料和四个唯一席位；
5. 比较快照与隐藏答案；
6. 只发出一次 `game_finished(outcome, reason)`。

完整且正确时：

```text
outcome = success
reason = meeting_prepared
```

任一资料缺失、重复、占用不完整或位置错误时：

```text
outcome = failure
reason = incorrect_seating_assignment
```

达到请求上限由现有 Python Session 发起统一终局：

```text
outcome = failure
reason = max_requests
```

首次终局后，重复按钮信号、Carryable 延迟信号、碰撞离开事件和交互请求全部成为幂等空操作，
不得改变冻结快照、世界摆放或发出第二次结果。Controller 继续负责验证合法终局并转发给 Bridge
和共享游戏结束界面。Monitor 提供与其他 Lobby 任务一致的 `show_result(outcome, reason)`。

## 请求上限与跨层契约

Python `ai_play.scenarios` 为本任务设置 200 次 `act` 请求硬上限；环境配置只能进一步收紧，
不能放宽。Godot Controller 和 Python registry 同步允许：

- `success/meeting_prepared`
- `failure/incorrect_seating_assignment`
- `failure/max_requests`

共享游戏结束界面增加中文结果和原因文本。轨迹结构、观察 DTO、桥协议版本和日志布局不变。

新增显式注册的 `arrange_meeting_briefings_briefing.py` loader。Briefing 只公开：

- 出生点附近任务卡和三个调查区域；
- 四份资料、四个环境席位和顺时针标记的通用规则；
- 资料可拿取、可信吸附、占用拒绝和提交前可调整；
- Verify 只有一次机会；
- 最多 200 次 `act` 请求；
- 通用移动、观察、探测、交互和可读物使用方法。

Briefing 可以复用现有受大小限制的 Lobby 参考图，但必须明确参考图不代表本局线索或答案。它
不得包含三个记录的实际文字、seed、hidden、solution、permutation、candidate、clue 类型结构、
内部席位 ID、场景路径或节点名。

## 推理指标扩展边界

本次不新增公开分析字段。Monitor 和席位组件为以下可信事件保留集中入口，未来可以增加私有
计数：

- 三份记录的首次读取顺序和重复次数；
- 首次读完全部记录时的请求数；
- 资料拿取、放置和重新调整次数；
- 向占用席位放置或携带非任务物体等无效操作；
- 达到正确排列后的误操作；
- 观察次数、移动距离和 MCP 请求数。

这些计数不得向玩家提供中途正确性反馈，也不得公开隐藏答案。

## 测试设计

### 纯回合模型

- 同一非零 seed 生成相同答案、线索顺序和记录分配；
- 多组 seed 的答案始终是四份资料到四个席位的一对一排列；
- 三条生成线索均与隐藏答案一致；
- 三条线索共同过滤 24 个排列后只有隐藏答案；
- 删除任意一条线索后至少有两个合法排列；
- 每条线索单独有效，三条线索没有规范重复；
- 五种线索求值、相邻、相对和顺时针方向语义正确；
- 记录分配始终是三条线索到三个区域的一对一排列。

### 席位交互与 Monitor

- 有效资料放入空席位时正常释放、清零、冻结、对齐并登记；
- 已占用席位拒绝新资料且不释放手持物；
- 非任务物体被拒绝；
- 拿起已放资料立即清除双向可信映射，之后可放到另一席；
- 重复放置、取回和延迟信号保持幂等；
- 提交前可任意调整，不产生成功/失败反馈；
- 正确完整映射产生一次 `success/meeting_prepared`；
- 错误或未完成映射产生一次 `failure/incorrect_seating_assignment`；
- Verify 后资料、席位和按钮锁定，重复事件不产生第二次终局。

### 场景隔离与跨层

- Monitor 是 Controller 的直属子节点，`scenario_id` 和 NodePath 正确；
- Setup 含三个固定区域记录、四份具名资料、四席、顺时针标记、Verify 和入口锚点；
- 选中任务时玩家、任务卡、记录、资料、席位和 Verify 正确启用；
- 未选中任务时 Setup 完全惰性，普通 Lobby 和其他任务行为不变；
- Python 场景白名单、briefing、200 次上限和三个终局结果正确；
- Controller 终局白名单和游戏结束文案与 Python 同步；
- 序列化 briefing、MCP 结构化结果和公开终局不含隐藏答案或生成状态。

最终按由小到大的顺序运行纯模型、席位交互、Monitor、Controller、Python
briefing/scenario/session、Lobby 静态检查、受影响的完整 AI Play 测试和密钥扫描，最后运行
`git diff --check`。
