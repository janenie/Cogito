# Conveyor Profit 公开菜单 Briefing 设计

## 背景

`conveyor_profit` 的六道菜谱固定展示在场景菜单板上，本来就是人类玩家可见的公开规则。
真实 AI 游玩表明，1024×576 截图中的菜单文字不足以稳定辨认：模型会误读蘑菇蛋卷配方，
继而用失败结果猜测新的组合。这个问题干扰了游戏真正要考察的能力——识别当前窗口的食材、
判断能完成哪些菜，并选择净利润最高的一道。

## 目标

在 `conveyor_profit` 的白名单 `briefing` 中增加一份结构化公开菜单。菜单完整描述六道固定
菜谱的名称、食材、售价和净利润，使黑盒玩家不再依赖菜单小字 OCR，同时保留对当前窗口
食材的视觉判断和利润计算任务。

## 公开契约

`briefing` 新增 `menu` 数组，每个元素包含：

- `id`：稳定的公开菜谱标识；
- `name`：面向玩家的英文全名；
- `ingredients`：制作一份菜所需的公开食材名数组；
- `sale_price`：公开售价；
- `net_profit`：按固定食材成本计算的公开净利润。

菜单包含且仅包含 `salad`、`egg_toast`、`cheese_toast`、`burger`、
`fish_sandwich` 和 `mushroom_omelet`。屏幕上的六张菜单贴纸继续保留，不改变人类玩法、
经济结算、窗口生成、语义动作或终局阈值。

## 安全边界

固定菜单属于场景中持续可见的公开规则，可以通过 briefing 白名单公开。以下信息仍不得进入
briefing：

- 当前窗口能完成的两道菜或最优菜；
- 当前或未来窗口的生成食材、随机种子和顺序；
- 单窗口或整局理论最优总额、通过额度的具体隐藏金额；
- 场景源码、节点路径、内部类名、开发者日志和测试事实。

AI 仍必须从 `observe` 截图判断当前传送带上有哪些食材，并自行把这些视觉证据与公开菜单
进行匹配和利润比较。

## 一致性与失败处理

Python briefing 中维护显式的公开菜单副本。自动测试锁定六道菜的标识、食材、售价和净利润，
并与当前 Godot 菜谱目录的公开值逐项对应。修改菜谱时，两端必须在同一个变更中同步更新；
缺项、额外项或数值不一致均视为测试失败。

briefing 加载仍返回新副本，调用方修改返回值不得污染后续运行。这个改动不增加新的文件读取、
网络访问或运行时持久化。

## 验证

1. 先添加失败测试，要求 `conveyor_profit` briefing 返回精确的六道结构化菜单。
2. 实现最小公开菜单常量并让测试通过。
3. 运行 briefing、scenario registry 和 MCP server 相关 Python 测试。
4. 运行受影响的完整 Python 测试及静态安全检查。
5. 运行一次真实 3 局 AWM 验收，确认模型直接使用 briefing 菜谱，但仍根据截图选择当前食材。
6. 最后运行 `git diff --check`，不提交截图、轨迹、运行时 memory 或缓存。
