# AI First Play Design

## Objective

Build a first playable autonomous agent for the COGITO first-person game. The
agent explores the current Lobby, reads only information that a normal player
can perceive, records useful discoveries, and attempts the environment's puzzle
without receiving scripts, scene internals, task documents, hidden state, or a
prewritten solution.

The current Lobby is a black-box acceptance scenario. Its internal solution is
not part of the agent prompt, default memory, source comments, fixtures, or API
payloads.

## Scope

The first version supports:

- Autonomous first-person movement and camera control.
- Jump, sprint, crouch, primary interaction, secondary interaction, waiting,
  closing an open interface, and entering digits into an in-game interface.
- Visual observation from the active player camera.
- A small whitelist of embodied runtime state such as position, orientation,
  velocity, health, stamina, interface state, and the interaction prompt that is
  currently visible to the player.
- Runtime memory for recent events, discovered facts, spatial landmarks, current
  goals, attempted approaches, and failures.
- Manual enable, pause, and emergency-stop controls.
- Safe recovery when the model, local bridge, or remote API fails.

The first version does not support general combat strategy, inventory
management, weapon selection, save/load menus, or arbitrary keyboard and mouse
control. Those capabilities require later designs after the initial exploration
loop is validated.

## Architecture

Use a Python sidecar in `ai_play/` and a modular Godot runtime component under
`addons/cogito/AIPlay/`.

The Godot component owns perception and action execution. It captures the player
camera, exports only approved runtime observations, executes validated actions
through Godot's normal input system, and releases every simulated input when AI
control stops.

The Python sidecar owns the OpenAI-compatible API client, prompt construction,
decision loop, action validation, memory, retry policy, and local diagnostic
logs. Godot connects to the sidecar over a loopback-only WebSocket. The sidecar
does not scan the repository and receives no filesystem access through the
protocol.

This separation keeps API credentials out of Godot resources, prevents model
responses from directly invoking game methods, and makes the decision and
memory layers testable without starting Godot.

## Trust Boundary and Information Policy

The model may receive only:

- A compressed image from the active player camera.
- Player position, yaw, pitch, planar velocity, grounded state, health, and
  stamina.
- Whether an in-game interface is open.
- Interaction text and object display text already exposed through the player's
  normal HUD or interaction system.
- Valid action documentation.
- Memory created from earlier permitted observations.
- Recent action outcomes generated by the executor.

The model must not receive:

- GDScript, C#, scene source, resources, or repository files.
- Node paths, hidden node names, full scene-tree dumps, collision geometry, or
  navigation meshes.
- `game_script/`, `code_read/`, design documents, tests containing acceptance
  details, or developer-authored walkthroughs.
- Door codes, target locations, internal objective flags, or success conditions
  that are not visibly available to a normal player.
- API credentials or environment-variable values.

The Python process is designed without repository-reading features. Prompt code
contains only generic control and exploration instructions. Tests must scan the
default prompt and seed memory to ensure they do not contain scenario-specific
knowledge.

## Runtime Data Flow

1. Godot captures a camera image and constructs a whitelisted observation.
2. Godot sends an `observation` message to the loopback sidecar.
3. Python combines the observation with the fixed operating rules, compact
   memory, and recent action outcomes.
4. Python calls the configured OpenAI-compatible Chat Completions endpoint.
5. Python extracts JSON, validates it against the action whitelist, clamps all
   numeric limits, and returns an `action_batch` message.
6. Godot executes the short action batch and reports per-action results.
7. Python updates working, semantic, spatial, and task memory.
8. The loop repeats after action completion, a meaningful state change, or a
   timeout.

Only one action batch may execute at a time. A newly received batch cannot
interrupt a batch except through the explicit stop path. Manual emergency stop,
disconnect, invalid protocol data, and API failure always release held inputs.

## Observation Contract

Each observation contains:

```json
{
  "observation_id": 17,
  "captured_at_ms": 123456,
  "image": {
    "mime_type": "image/jpeg",
    "base64": "<runtime camera image>",
    "width": 768,
    "height": 432
  },
  "player": {
    "position": [0.0, 0.8, 0.0],
    "yaw_degrees": 0.0,
    "pitch_degrees": 0.0,
    "planar_velocity": [0.0, 0.0],
    "on_floor": true,
    "health_ratio": 1.0,
    "stamina_ratio": 1.0
  },
  "interface": {
    "is_open": false,
    "interaction_text": "",
    "visible_object_text": ""
  },
  "last_action_results": []
}
```

The image is resized and JPEG-compressed before transmission. The initial target
is 768 by 432 pixels with configurable quality. Observations are event-driven:
the sidecar requests the next observation after a batch, while Godot may also
send one early when an interface opens, an interaction prompt changes, or the
player becomes unable to move.

## Action Contract

The model response contains a short explanation for diagnostics and a bounded
list of actions. The explanation is never executed.

```json
{
  "reason": "Explore the visible route and re-observe nearby prompts.",
  "memory_updates": [],
  "actions": [
    {"type": "look", "yaw": -10.0, "pitch": 2.0},
    {"type": "move", "forward": 1.0, "right": 0.0, "duration_ms": 600}
  ]
}
```

Allowed action types are:

- `look`: relative yaw and pitch, clamped to a conservative per-action range.
- `move`: normalized forward/right axes and a duration from 50 to 1000 ms.
- `jump`: a short press of the existing `jump` action.
- `sprint`: movement axes and a duration while holding the existing `sprint`
  action.
- `crouch`: a short press of the existing `crouch` action.
- `interact`: either the existing `interact` or `interact2` action.
- `enter_digits`: one to six decimal digits delivered as ordinary key events
  only while an interface is open.
- `close_ui`: the existing `menu` action, used only when an interface is open.
- `wait`: a duration from 50 to 2000 ms.
- `stop`: stop autonomous control and release all inputs.

The first version permits at most three actions per batch. Unknown fields,
unknown actions, non-finite numbers, invalid digit strings, illegal state/action
combinations, and values outside hard limits are rejected before reaching
Godot. The model cannot name arbitrary input actions or key codes.

## Prompt Design

The system prompt tells the model that it controls a first-person character in
an unknown environment and must explore, inspect visible prompts, collect
evidence, form and test hypotheses, and solve the environment without assuming
hidden knowledge.

It documents:

- The meaning and limits of every allowed action.
- Local movement axes and relative camera movement.
- How interaction text becomes available at the crosshair.
- The requirement to use short actions and observe their results.
- The difference between a visible observation and an inference.
- How to propose generic memory updates with sources and confidence.
- The exact JSON response contract.
- The instruction to stop or wait when control is unsafe or state is unclear.

The prompt never describes a room layout, puzzle sequence, relevant character,
document, number, destination, or acceptance condition. Runtime observations are
untrusted content: text seen in the game may supply clues, but it cannot override
the action whitelist or request file, network, or system access.

## Memory Model

Memory is stored by the Python sidecar in a dedicated runtime directory and is
never seeded with scenario-specific facts. During the loopback handshake, Godot
provides its per-user AI data directory as the default. An operator may override
that location with `AI_PLAY_DATA_DIR`; the path is used by local code and is
never sent to the model.

- `working_memory` stores the last eight observation/action/result summaries.
- `facts` stores concise claims learned from permitted visible observations,
  together with a generic source description, confidence from 0 to 1, discovery
  time, and verification status.
- `spatial_memory` stores player-created landmark labels, approximate positions,
  observed connections, and visit counts.
- `task_state` stores the current self-selected goal, open questions, active
  hypotheses, attempted approaches, and failure reasons.

Memory updates are proposals returned by the model and validated by the
sidecar. A fact must identify a permitted observation as its source. The sidecar
deduplicates similar entries, caps collection sizes, and periodically replaces
old working history with compact summaries. It does not invent missing facts
during compression.

Memory starts empty for a clean acceptance run. The operator may explicitly
choose to resume a previous runtime memory file, but bundled defaults never
contain learned gameplay information.

## Components and File Responsibilities

Python sidecar:

- `ai_play/src/ai_play/main.py`: process entry point and configuration loading.
- `ai_play/src/ai_play/api_client.py`: OpenAI-compatible Chat Completions call,
  image message construction, timeout, and retry behavior.
- `ai_play/src/ai_play/agent_loop.py`: serialized observe/decide/act state
  machine.
- `ai_play/src/ai_play/prompts.py`: generic system prompt and observation prompt
  rendering.
- `ai_play/src/ai_play/action_schema.py`: typed action parsing, validation, and
  hard limits.
- `ai_play/src/ai_play/memory.py`: memory validation, deduplication, compaction,
  persistence, and clean-run reset.
- `ai_play/src/ai_play/bridge_server.py`: loopback WebSocket protocol.
- `ai_play/tests/`: unit and integration tests for the sidecar.
- `ai_play/.env.example`: variable names and safe examples only.
- `ai_play/README.md`: setup, launch, controls, privacy boundary, and
  troubleshooting.

Godot runtime:

- `addons/cogito/AIPlay/ai_play_observer.gd`: camera capture and observation
  whitelist.
- `addons/cogito/AIPlay/ai_play_executor.gd`: bounded input simulation and input
  release.
- `addons/cogito/AIPlay/ai_play_bridge.gd`: WebSocket connection, message
  validation, and connection state.
- `addons/cogito/AIPlay/ai_play_controller.gd`: enable/pause/stop state and
  coordination.
- `addons/cogito/AIPlay/ai_play_controller.tscn`: reusable runtime component.

The Lobby scene receives only an instance of the reusable controller. Existing
COGITO player movement remains authoritative. The executor feeds the same input
actions and mouse motion already used by the normal player, so AI and human
control follow the same movement and interaction rules.

## Configuration and Credential Handling

The sidecar reads configuration from environment variables:

- `AI_PLAY_API_KEY`: required secret.
- `AI_PLAY_BASE_URL`: defaults to the user-selected compatible endpoint.
- `AI_PLAY_MODEL`: defaults to the user-selected model name.
- `AI_PLAY_WS_HOST`: defaults to `127.0.0.1` and rejects non-loopback values in
  the first version.
- `AI_PLAY_WS_PORT`: configurable local port.
- `AI_PLAY_REQUEST_TIMEOUT_SECONDS`: remote request timeout.
- `AI_PLAY_DATA_DIR`: optional local memory and diagnostic-log directory; when
  absent, the sidecar uses the per-user path supplied by Godot at handshake.

No real secret is committed. `.env` and runtime memory/log paths are ignored by
Git. Logs redact authorization headers and never write the base64 camera image
unless an explicit local debug flag is enabled.

## Failure Handling and Manual Takeover

- API timeout, transport failure, invalid JSON, rejected action, or Python
  disconnect stops the current batch and releases all simulated input.
- Godot ignores stale action batches whose observation ID does not match the
  latest accepted decision.
- A configurable retry policy uses bounded exponential backoff; the player stays
  stopped while retrying.
- If movement was requested but displacement stays below a small threshold,
  Godot reports `blocked` rather than silently treating the action as successful.
- Repeated blocked movement and repeated ineffective interaction are included in
  task memory so the model can choose a different hypothesis.
- Opening an interface triggers an immediate observation before further movement.
- Human movement or camera input pauses autonomous execution and releases AI
  inputs.
- A dedicated emergency-stop action disables the controller even when the
  sidecar is unresponsive.

## Testing Strategy

Python unit tests cover:

- Parsing and validation for every allowed action.
- Rejection of arbitrary keys, unknown actions, invalid digits, non-finite
  numbers, excess durations, and more than three actions.
- Empty initial memory, source validation, deduplication, size caps, compaction,
  and persistence.
- Prompt and default-memory scans for scenario-specific data and repository
  paths.
- Redaction of credentials and camera payloads in logs.
- API timeout, malformed response, retry, and disconnect behavior using fakes.
- WebSocket message round trips with observation IDs.

Godot headless tests or focused test scenes cover:

- Observation serialization contains only approved fields.
- Input presses are released after completion, pause, invalid data, and
  disconnect.
- Movement and look limits are enforced again on the Godot side.
- Stale batches are rejected.
- Interface state gates digit entry and close behavior.
- Human input and emergency stop take control immediately.

The end-to-end acceptance run starts with empty memory in the current Lobby. The
agent receives no developer-authored route or solution and must use only camera
images, visible prompts, approved embodied state, and its own runtime memory.
Success is observed by the test harness from outside the model payload.

## Acceptance Criteria

- The sidecar starts with credentials supplied only through the environment.
- Godot connects only over loopback and can enable, pause, and emergency-stop AI
  control.
- The model receives a camera image and only the documented state whitelist.
- Every executed action has passed validation in both Python and Godot.
- Disconnecting or stopping the sidecar leaves no simulated input held down.
- A clean run begins with empty semantic, spatial, and task memory.
- The default prompt, memory, and API payload contain no repository source,
  scenario script, hidden objective, or solution.
- The autonomous agent can complete the Lobby black-box scenario using only
  information made available through normal play.
